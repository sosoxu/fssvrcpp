# ADR-007：异步/协程的采纳策略 —— 分层决策，而非整体重写

- 状态：**已采纳（Accepted）** —— "现在做什么"与"什么时候才做"分开决策
- 日期：2025
- 相关：`docs/05-capacity-and-concurrency.md`、`docs/adr/ADR-002-http-framework.md`、
  `docs/adr/ADR-006`（大文件数据面，拟定）、`docs/appendix/coroutine-probe/`

---

## 1. 问题

需求方问："**使用协程是否能够提高并发？**"

这个问题不能一句话回答，因为答案取决于**等待的是什么**。本 ADR 用实测把它拆开回答。

---

## 2. 实测（全部在本机 16 核 / GCC 11 / Ubuntu 22.04）

探针源码与复现方式：`docs/appendix/coroutine-probe/`。

### 2.1 前提验证（先确认可行）

| 项 | 结果 |
| --- | --- |
| C++20 协程基础能力（`g++ -std=c++20`） | ✅ 可用（`__cpp_impl_coroutine = 201902`） |
| `std::generator` | ❌ 不可用（需 GCC 14 / C++23） |
| `std::execution`（senders/receivers, P2300） | ❌ 不可用（`__cpp_lib_execution` 指的是**并行算法**，不是 P2300，易误读） |
| **Boost.Asio 1.74 + C++20 协程**（`awaitable`/`co_spawn`） | ✅ **编译并实际运行成功**（`libboost1.74-dev` 可 apt 解包，162 MiB 头文件） |
| 内核 io_uring | 内核 6.18.33（WSL2），`io_uring` 符号存在；`liburing-dev` 2.1 可获取（**WSL2 上的实际可用性未验证**） |

### 2.2 线程模型 vs 协程模型（每请求 5 ms I/O 等待，2048 并发 keep-alive）

独立客户端进程（绑 4 核），同一负载：

| 模型 | 配置 | OS 线程 | RSS | 吞吐 | 实测并发 |
| --- | --- | --- | --- | --- | --- |
| **线程**（httplib） | pool=64 | 65 | 4.7 MB | 12,679 req/s | 64 |
| **线程**（httplib） | pool=512 | 513 | 10.3 MB | 79,970 req/s | 512 |
| **线程**（httplib） | pool=2048 | **2,049** | **29.3 MB** | 127,026 req/s | **1,273**（未达 2048，err=96） |
| **协程**（Asio） | 4 io 线程 | **4** | **3.1 MB** | **230,437 req/s** | 2048 |
| **协程**（Asio） | 16 io 线程 | **16** | **3.3 MB** | **254,549 req/s** | 2048 |

**结论：协程用 16 个线程达到 254k req/s，线程模型用 2049 个线程只有 127k req/s。**

| 对比维度 | 优势 |
| --- | --- |
| 吞吐 | **2.0x** |
| OS 线程 | **128x 少** |
| RSS | **~9x 少** |
| 可达并发 | 线程模型 2048 线程也**只到 1273 并发**且出现错误；协程稳定达 2048 |

### 2.3 ★ 决定性实验：协程本身不等于异步

**同一个协程服务端、同样 4 个 io_context 线程、同样 2048 并发连接、同样 50 ms 等待**，
只改变"如何等待"：

| mode | 实现方式 | 吞吐 | 相对 |
| --- | --- | --- | --- |
| 0 | 协程内**直接阻塞调用**（`sleep` 占住 io 线程） | **763 req/s** | 1x |
| 1 | 协程内 **offload 到 64 线程池** | **758 req/s** | 1x |
| 2 | 协程内**真正异步等待**（`steady_timer`） | **40,246 req/s** | **52x** |

mode 2 的 40,246 req/s ≈ 2048 ÷ 0.05 = **理论满并发**，即用 4 个线程达到了 2048 的并发度。

**这就是全部答案的核心**：

> 协程的价值来自"**在等待时让出执行权**"。
> 如果协程里调用的是**阻塞 API**，它不会让出，**整个 io_context 线程被占住** ——
> 此时协程的并发度退化为 **io 线程数**，比线程模型**更差**（线程模型至少能达到 pool 大小）。
> 把阻塞调用 offload 到线程池，只是把并发上限换成"池大小"，**等价于线程模型**，没有额外收益。

## 3. 应用到本项目：哪些等待能真正异步化

| 本项目的等待 | 能否真正异步 | 说明 |
| --- | --- | --- |
| **TCP socket 收发** | ✅ 可以 | `async_read/async_write` 是真异步（epoll）。**这是协程的主要收益来源** |
| **对象存储 HTTP 调用（libcurl）** | ⚠️ 部分 | libcurl 的 easy 接口是阻塞的；必须改用 **multi 接口**（事件驱动）才能异步。否则只能 offload |
| **SQLite 读写** | ❌ 不能 | 无异步 API。只能 offload 到专用线程池 → **并发上限 = 池大小** |
| **POSIX 文件 `pread/pwrite`** | ❌ 不能（默认） | 阻塞系统调用。要么 offload，要么用 **io_uring** |
| **`sendfile` 零拷贝发送** | ❌ 不能（默认） | 同样是阻塞调用 |
| **fsync** | ❌ 不能 | 阻塞 |
| **CPU 密集（memcpy/校验和）** | ❌ 无关 | 协程不减少 CPU 工作量 |

**关键推论**：
- 对**对象存储模式**，"大量频繁小文件"的字节传输**不经过服务**（客户端直连预签名 URL）→ **协程对该路径毫无作用**。
- 对**集中存储模式的 POSIX 数据面**，`pread`/`sendfile` 都是阻塞的 → **除非引入 io_uring，协程只能改善 socket 侧的多路复用**。
- **SQLite 是控制面的真实天花板**（实测 WAL+`NORMAL` 约 **25,000 事务/秒**），
  而线程模型在 pool=512 时已达 **79,970 req/s**、pool=2048 时 **127,026 req/s**
  → **控制面在 DB 成为瓶颈之前，线程模型已经够用**。此时上协程是提前优化。

## 4. 决策：分三步，按实测门槛推进

### 第 1 步（现在，P1–P4）：保持线程模型，先把免费的部分做完

| 动作 | 依据 |
| --- | --- |
| `TCP_NODELAY=true`（服务端+客户端） | 950x（`docs/05` §1.2） |
| 线程池按"并发连接数"配置，不按核数 | 线程池=并发硬上限（`docs/05` §1.3） |
| 控制面/数据面线程池分离 + 503 背压 | 防止大文件传输饿死元数据请求 |
| SQLite 优化（`NORMAL`、有界写并发 8、组提交） | DB 是真实天花板（25k tx/s） |
| `sendfile` 数据面（ADR-006） | 2.05x 吞吐、每 GiB CPU 少 42% |

**不做**：不引入 Asio/协程。理由：线程模型已达 127k req/s，**高于 SQLite 天花板 25k tx/s 5 倍**，
瓶颈不在线程；此时换 I/O 栈是无收益的高风险重写。

### 第 2 步（触发条件达成时）：数据面异步化

**触发条件（任一满足才启动）**：

| # | 条件 | 依据 |
| --- | --- | --- |
| T1 | 实测需要维持 **> 2,000** 个并发连接（长连接/慢客户端/TB 级读并发） | 线程模型在 2048 线程时只达 1,273 并发且出错（§2.2） |
| T2 | 实测控制面在 **DB 优化后**仍受线程数限制（线程数已超 512 且 CPU 未饱和） | 排除 DB 为瓶颈后，才轮到线程 |
| T3 | 数据面 socket 侧成为瓶颈（存储/网卡未饱和但吞吐上不去） | 说明等待在 socket 而非磁盘 |

**做法**：为数据面引入 Asio + 协程（该面只需 `GET`/`HEAD` + `Range` + 鉴权，范围可控），
并**同时**评估 io_uring 以异步化 `pread`/`sendfile`。**不触碰控制面。**

### 第 3 步（仅在第 2 步验证有效后）：控制面异步化

只有第 2 步的收益被实测确认、且控制面确实成为瓶颈时，才考虑把控制面（19 个 OSDU 端点）迁到 Asio + 协程。
**这一步代价最大**（等于在 Asio 上重写 HTTP 层，见 §5），必须有实测收益支撑。

## 5. 成本与风险（为什么"不整体重写"是理性选择）

| 成本项 | 说明 |
| --- | --- |
| **必须放弃 httplib** | httplib 是**线程-每连接**架构，**零协程支持**。协程意味着换 Asio 并自行实现 HTTP 解析/路由/keep-alive |
| **依赖体积** | Boost 头文件解包后 **162 MiB**（对比 httplib 单头文件 405 KB）；需评估是否只抽取 Asio 子集 |
| **阻塞 API 需要逐个处置** | SQLite（offload）、libcurl（改 multi 或 offload）、`pread`/`sendfile`（io_uring 或 offload）、fsync（offload） |
| **io_uring 在本环境未经验证** | 内核是 **WSL2 6.18**，`io_uring` 在 WSL2 上历史上支持不完整；`liburing` 头文件需 apt 解包。**列为待验证项** |
| **调试复杂度上升** | 协程挂起/恢复、栈帧生命周期、跨执行器 hop 的时序问题，比线程模型更难定位 |
| **收益不对称** | 控制面收益被 SQLite 天花板吃掉；对象存储模式收益为零；只有 POSIX 数据面 + 高连接数才有收益 |

**与 ADR-002 的教训一致**：这次不重犯"用一个局部问题推出整体重写"的错误。
协程是**有明确适用边界的工具**，本 ADR 用触发条件（T1–T3）把它约束在需要的地方。

---

## 6. 后果

- **正面**：避免了在收益不明确时重写整个 I/O 栈；同时给出了明确的"何时该做"的量化触发条件，
  不会因为"协程听起来更好"而反复摇摆。
- **负面 / 风险**：
  - 若 T1–T3 很快达成，第 2/3 步会成为关键路径 → 缓解：把数据面设计成**可替换的传输实现**
    （接口与 httplib 解耦，见 ADR-006），使第 2 步不需要动业务代码。
  - 团队若不熟悉协程，学习成本落在第 2 步 → 缓解：先用数据面（范围小、逻辑简单）试水。
- **明确记录**：`std::generator` 与 P2300 `std::execution` 在本环境不可用，
  因此协程实现必须基于 **Boost.Asio 的 `awaitable`**，不能依赖标准库协程设施。

## 8. ★ 专项补充：POSIX 集中存储的大量 I/O 到底该不该用协程异步？

> 触发问题："集中存储模式下有大量的 IO 操作，是否用协程异步的方式更好？"
> 实测原始输出：`docs/appendix/posix-io-probe/RESULTS.txt`；探针源码同目录。
> 本机 16 核 / WSL2 内核 6.18.33（**非真实部署环境**，绝对数字仅作量级参考）。

### 8.1 先测"单次 I/O 延迟"——这是决定答案的那个数字

吞吐 = 并发 ÷ 延迟。所以延迟决定了"需要多少并发"，也就决定了线程模型够不够。

| I/O 形态 | 平均延迟 | p99 | **单线程上限** |
| --- | --- | --- | --- |
| **页缓存命中**（4 KiB 随机读） | **0.7 µs** | 1.1 µs | **1,534,599 ops/s** |
| **O_DIRECT**（绕过页缓存，真实设备） | **120.9 µs** | 235.7 µs | **8,269 ops/s** |
| **写 4 KiB + fsync** | **1,438.7 µs** | 2,757 µs | **695 ops/s** ⚠️ |
| 写 4 KiB（无 fsync） | 1.8 µs | 15.2 µs | 565,897 ops/s |

**三个立刻可用的结论**：

1. **缓存命中的读，协程毫无价值**：0.7 µs/次 → 单线程就能做 150 万次/秒。任何异步化的开销都是净损失。
2. **非缓存读 121 µs**：单线程 8,269 ops/s；要 100k IOPS 需要 ~12 个并发。
3. **`fsync` 是写入路径的绝对主导成本（1.44 ms）**，比读慢 1,700 倍。
   单线程只能做 **695 文件/秒** —— 这才是"大量小文件写"的真正瓶颈。

### 8.2 读路径：线程模型 vs io_uring（O_DIRECT 4 KiB 随机读）

| 模型 | 并发 | IOPS | 聚合带宽 |
| --- | --- | --- | --- |
| 线程（阻塞 `pread`） | 16 线程 | 73,920 | 289 MiB/s |
| 线程（阻塞 `pread`） | 32 线程 | 108,096 | 422 MiB/s |
| 线程（阻塞 `pread`） | 64 线程 | 111,663 | 436 MiB/s |
| 线程（阻塞 `pread`） | **128 线程** | **118,148** | 461 MiB/s ← 设备饱和 |
| **io_uring（手动 submit/reap）** | **1 线程，深度 64** | **132,934** | **519 MiB/s** ← 设备饱和 |
| io_uring | 1 线程，深度 256 | **136,491** | 533 MiB/s |
| io_uring | 1 线程，深度 1024 | 136,172 | 532 MiB/s（无进一步收益） |

**结论**：
- **io_uring 用 1 个线程达到 132,934 IOPS，比 128 线程的 118,148 IOPS 还高 13%**（后者被上下文切换拖累）。
- **但吞吐上限是设备（~133–136k IOPS / ~533 MiB/s），异步不能突破它。**
  所以异步在读路径上的收益是"**用 1 个线程替代 64–128 个线程**"，而不是"提升吞吐上限"。
- 32 线程已经拿到设备能力的 **79%**，64 线程 **82%**。若目标吞吐低于 ~80k IOPS，**线程模型足够**。

### 8.3 写路径：★ 真正的杠杆不是协程，是"摊销 fsync"

| 方案 | 文件/秒 | 每文件耗时 | 相对最佳 |
| --- | --- | --- | --- |
| 1 线程，每文件 `fsync` | 760 | 1.32 ms | 1x |
| 16 线程，每文件 `fsync` | 5,900 | 0.17 ms | 8x |
| 64 线程，每文件 `fsync` | 16,104 | 0.06 ms | 21x |
| **io_uring**（深度 16，`write`+`fsync` 链式，单线程） | **20,497** | 0.05 ms | **27x** |
| io_uring（深度 64 / 256） | ~16,300 | 0.06 ms | 21x |
| ~~组提交（16 线程，每 500 文件 1 次 `fsync`）~~ | ~~58,741~~ | ~~0.017 ms~~ | ⚠️ **该行已作废，见下方更正** |
| 组提交（64 线程） | ~~59,248~~ | — | ⚠️ 同上 |

> ### ⚠️ 更正（2025，由 ADR-008 的耐久性验证发现）
> 上表两行的基准实现**没有对文件数据做 `fsync`**（顺序是 `write → rename → 批末 fsync(dir)`），
> 违反"数据先落盘再改名"的不变量，**断电后可能产生"文件存在但内容为空/残缺"**。
> 因此 **58,741 文件/秒 是一个不安全协议的数字，不能作为设计依据**。
>
> 经 **[ADR-008](ADR-008-write-durability-protocol.md)** 的验证，正确数字是：
>
> | 协议 | 文件/秒 | 安全性 |
> | --- | --- | --- |
> | 每文件 `fdatasync` + 每文件 `fsync(dir)`（严格） | 383 | ✅ |
> | 每文件 `fdatasync` + 每批 `fsync(dir)` | 784 | ✅ |
> | **两阶段批提交（写批→`syncfs`→统一 `rename`→`fsync(dir)`）** | **31,478** | ✅ **推荐** |
> | 无数据 `fsync` + 每批 `syncfs`（本文档原方案） | 35,389 | ❌ **不安全** |
>
> **结论方向不变**（摊销 fsync 仍是最大杠杆，比严格做法快 82x），
> **但协议与数字必须按 ADR-008 修正**；而且"不安全方案只快 11%"，
> 说明**根本不存在"用安全换性能"的取舍**。

**结论（本 ADR 最重要的一条）**：

> **组提交比 io_uring 快 2.9x，比 64 线程快 3.6x，而且它不改变 I/O 模型** ——
> 纯粹是"把 fsync 摊到一批文件上"的算法/策略改动。
> 协程、io_uring 都动不了 fsync 的物理成本（1.44 ms 是设备 flush 时间），
> **只有减少 fsync 的次数才能真正解决写入瓶颈。**

代价是耐久性粒度：组提交下崩溃最多丢一批（如 500 个文件），而不是 1 个。
这正是 `fsync_policy: by_size` + `group_commit_max_batch` 要表达的策略，必须在配置与文档中显式说明。

### 8.4 因此对 POSIX 集中存储的结论

| 路径 | 推荐 | 依据 |
| --- | --- | --- |
| **缓存命中读**（元数据、热点小文件） | **线程模型**；不要异步 | 0.7 µs/次，单线程 150 万 ops/s；异步是净开销 |
| **非缓存读**（冷数据、TB 文件分段） | 线程够用（32–64 线程达设备 79–82%）；**若要 1–2 个线程吃满设备或需要 >2,000 并发，用 io_uring** | 1 线程 133k IOPS vs 128 线程 118k IOPS |
| **小文件写** | **优先做组提交与 fsync 摊销**；io_uring 次之；协程无关 | **两阶段批提交 31,478 文件/s**（ADR-008）vs io_uring 20,497 vs 64 线程 16,104 |
| **大文件顺序读（TB 级分段）** | `sendfile` 零拷贝（ADR-006）；io_uring 可叠加 | `sendfile` 2.05x 吞吐、每 GiB CPU 少 42%（`docs/05` §1.7） |

**逐条回答"是否用协程异步更好"**：

1. **不是"协程"更好，而是"异步文件 I/O"更好** —— 而且这靠的是 **io_uring**，不是协程。
   上表的 io_uring 数据是**用手写 submit/reap 循环、零协程**跑出来的（见 `uring_bench.c`）。
   **io_uring ≠ 协程**：你可以只用 io_uring + 简单状态机，就拿到全部收益，
   不需要引入 Boost.Asio、不需要协程、不需要重写控制面。
2. **协程只是 io_uring 之上的"语法糖"**：它让"大量在途操作"的代码更好写（`co_await read(...)`
   而不是手写状态机），但它本身不带来性能。§2.3 已证明：协程里放阻塞调用，性能反而腰斩再腰斩。
3. **写入路径的收益排序与"异步"无关**：组提交（2.9x）> 减少 fsync（大幅）> io_uring（1.27x）> 协程（0）。
4. **绝不要在缓存命中路径上引入异步**：0.7 µs 的操作，任何调度开销都占比过高。

### 8.5 修正 ADR-006 的范围（重要）

原 ADR-006 只写了"自持 socket + `sendfile` 独立数据面"。依据本节数据，**范围应扩展为**：

```
集中存储数据面（独立监听器，不依赖 httplib）
├── socket 侧：自持 socket + sendfile/splice（零拷贝）
├── 文件侧：io_uring（异步 pread/write/fsync），队列深度按 §8.2/§8.3 取 64 左右
├── 实现形态：手写 submit/reap 事件循环 + 状态机（**协程可选，非必需**）
└── 边界不变：只承载 /v1/transfer 的 GET/HEAD + Range；控制面仍用 httplib
```

**升级理由**：io_uring 在本机已实测可用（`io_uring_queue_init` + 异步读成功），
且它在读路径上以 1 线程达到 128 线程的吞吐、在写路径上以 1 线程达到 64 线程的 1.27 倍。
**但 io_uring 可用性必须在目标部署内核上复核**（本机是 WSL2，不作为判定依据）——门槛 C9.18。
