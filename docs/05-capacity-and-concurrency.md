# 容量模型与并发设计（高并发 / 小文件 / TB 级大文件分段读）

> **本文档是对现有设计的自我审查结果。**
> 触发原因：明确实际负载为「**大量频繁读写小文件**」+「**读几十 GB ~ TB 级大文件的一部分，只读不写**」。
> 结论：**原设计的并发模型与数据面在这两个场景下都不达标**，本文给出实测依据与必须的修正。
> 所有数据均由 `docs/appendix/capacity-probe/` 中的探针在本机（16 核 / Ubuntu 22.04）实测得到。

---

## 0. 结论摘要（先看这个）

| # | 问题 | 严重度 | 修正 |
| --- | --- | --- | --- |
| **B-1** | 默认线程池 = `max(8, nproc-1)` = **15**，且**一条 keep-alive 连接占用一个线程直到连接结束** | 🔴 **致命** | 显式设置线程池；控制面与数据面**分离线程池**；配置项加"并发连接数"语义校验 |
| **B-2** | cpp-httplib `TCP_NODELAY` 默认 **false** | 🔴 **致命** | 强制 `set_tcp_nodelay(true)`（实测**950 倍**差距：23 → 21,000 req/s） |
| **B-3** | 集中存储（POSIX）模式下**每个字节都占用一个线程**，且 `sendfile` 不可用（httplib 不暴露 socket） | 🔴 **致命** | 大文件数据面独立进程 + `sendfile`（实测 **~5–7x**）；小文件高并发走对象存储模式（字节不经过服务） |
| **B-4** | SQLite `synchronous=FULL`（每事务 fsync）只有 **1,219 事务/秒**，而 `NORMAL` 有 **25,471/秒** | 🟠 高 | 默认 `NORMAL`；`fsync_on_write` 改为**按大小分级**策略而非全局开关 |
| **B-5** | 小文件每个要走 **2 次 DB 事务** + 可能的 `fsync` + 原子写（tmp+rename） | 🟠 高 | 批量提交/组提交；小文件跳过原子写；写入队列 |
| **B-6** | 原文声称"`fss_http` 负责 Range 归一化"——**过度设计**，httplib 的 content provider 本身已 Range 感知 | 🟡 中 | 声明**完整**大小即可，httplib 会传 `(offset,length)`；`fss_http` 只处理 416/越界等边界 |
| **B-7** | 原设计的并发/容量章节只有定性描述，无可执行数字 | 🟡 中 | 本文给出容量公式；实现计划新增容量门槛（P9） |
| **B-8** | 我自己的进程内"客户端+服务端同机"基准**不可信**（曾得出 T=32 比 T=4 慢 15 倍的假结论） | 🟡 中 | 负载生成器必须**独立进程**并绑核；写入 `docs/appendix/capacity-probe/README.md` 作为方法学要求 |

### 1.2 `TCP_NODELAY`：950 倍（**最重要的单点发现**）

同一服务端、同一客户端、keep-alive、小 JSON 响应：

| 服务端 `TCP_NODELAY` | httplib 客户端吞吐 | 平均延迟 |
| --- | --- | --- |
| **OFF（httplib 默认）** | **23 req/s** | **43.8 ms** |
| **ON** | **21,062 req/s** | **0.047 ms** |

43.8 ms ≈ 经典 **40 ms delayed-ACK** 特征：Nagle 算法让第二次小写入等待第一次的 ACK，
客户端延迟 ACK 定时器到期才回。**这是"小文件频繁读写"场景的隐形杀手**——
不修它，任何并发优化都白费。

> cpp-httplib 源码：`#define CPPHTTPLIB_TCP_NODELAY false`（`httplib.h:145`）。
> 必须显式 `svr.set_tcp_nodelay(true)` **且** `cli.set_tcp_nodelay(true)`。

### 1.3 线程池：并发硬上限

每请求 `sleep 5ms`（模拟存储 IO），统计**实际服务过请求的线程数**：

| 线程池 | 并发客户端 | 吞吐 | 服务线程数 |
| --- | --- | --- | --- |
| **默认（15）** | 8 | 74 req/s | 8 |
| **默认（15）** | 16 | 147 req/s | **15（封顶）** |
| **默认（15）** | 32 | 295 req/s | **15（封顶）** |
| **默认（15）** | 64 | 494 req/s | **15（封顶）** |
| `ThreadPool(256)` | 32 | 168 req/s | 32 |
| `ThreadPool(256)` | 64 | 216 req/s | 64 |

**两点结论**：

1. 默认池 = `max(8, nproc-1)` = **15**，是**硬上限**。32 个并发客户端只有 15 个能被服务。
2. **一条 keep-alive 连接会占用一个线程直到连接结束**（httplib 在池线程内循环处理同连接的后续请求）。
   因此**线程池必须 ≥ 预期并发连接数**，否则出现连接饿死。
   推论：`worker_threads` 不能按"核数"配，必须按"并发连接数"配。

> 注：本表的绝对吞吐偏低（216 req/s vs 理论 64/0.005 = 12,800），
> 因为客户端与服务端共享 16 核且客户端线程在 `sleep` 语义下争抢调度。
> **这张表用于证明"线程数 = 并发上限"这一结构性事实，不用于容量规划。**

### 1.4 独立负载进程下的真实扩展性

`pool=512`，独立 `loadgen` 进程（绑 4 核），1 MiB 随机分段读：

| 并发连接 T | 聚合吞吐 | 请求率 | `max_inflight`（服务端实测） |
| --- | --- | --- | --- |
| 4 | 3.21 GiB/s | 3,286 req/s | — |
| 16 | 3.70 GiB/s | 3,788 req/s | — |
| 32 | 3.28 GiB/s | 3,362 req/s | — |
| 64 | 3.15 GiB/s | 3,228 req/s | **64** |

**结论：并发是真实发生的（`max_inflight = 64 = 客户端数`），吞吐在 4→64 并发区间持平在 ~3.2–3.7 GiB/s。**
这个平台期是**测试环境的带宽/CPU 上限**，不是服务的并发上限。
（对比 §1.2 的错误测量：进程内客户端会得出"并发越高越慢"的假象。）

### 1.5 小段读的请求率上限（= 小文件读场景）

`pool=512`，独立客户端，64 连接：

| 段大小 | 请求率 | 吞吐 |
| --- | --- | --- |
| **4 KiB** | **35,206 req/s** | 0.13 GiB/s |
| **16 KiB** | **39,516 req/s**（峰值） | 0.60 GiB/s |
| 64 KiB | 24,009 req/s | 1.47 GiB/s |
| 256 KiB | 8,201 req/s | 2.00 GiB/s |

**结论：单节点小段读的请求率上限约 4 万 req/s**（含 `pread` + 内容提供者 + HTTP）。
小文件（4 KiB）可支撑 ~3.5 万次读/秒。这个量级对多数场景够用，但它是**每节点**上限。

### 1.6 大文件分段读的正确性（必须验证的硬要求）

| 项 | 结果 |
| --- | --- |
| **64 位偏移** | 在 200 GiB 文件的 **150 GiB 偏移**处读取，内容与写入的标记完全一致 ✅ |
| **无读放大** | 读 1 MiB 段：服务端耗时 **1.5 ms**，只读 1 MiB（若放大到全文件需数百秒） ✅ |
| **越界 Range** | → **416** ✅（0.26.0；0.10.3 会给出下溢的 `Content-Length`，见 ADR-002 H-1） |
| **段大小对吞吐的影响** | 8 MiB 段比 1 MiB 段吞吐高 ~50%（4.72 vs 3.02 GiB/s，见 §1.7） |

⚠️ **读路径的硬性禁令**（TB 级文件的正确性前提）：

1. **绝不在读路径计算校验和**（否则每次范围读都变成 O(文件大小)）；
2. **绝不在读路径 `stat` 之外扫描文件**；
3. `TotalSize` 用字符串（OSDU 要求），但**内部一律 `uint64_t`**，编译期强制
   `_FILE_OFFSET_BITS=64`，`pread/pwrite` 的 `off_t` 必须 64 位；
4. 单次 `sendfile` 上限约 2 GiB（`0x7ffff000`），**必须循环**（探针已按循环实现）。

### 1.7 `sendfile` vs `pread+write`：~2x，以及 httplib 的 ~7x 差距

| 实现 | 段=1 MiB | 段=8 MiB | 每 GiB CPU（1 MiB 段） |
| --- | --- | --- | --- |
| `pread + write` | 3.02 GiB/s | 4.72 GiB/s | 0.36 CPU-s |
| **`sendfile`** | **6.19 GiB/s** | **9.70 GiB/s** | **0.21 CPU-s** |

**sendfile 快 2.05x，每 GiB CPU 少 42%。**

再叠加 httplib 本身的路径开销（其 content provider 只能 `read()` + `write()`，且 handler
**拿不到 socket fd**，无法 `sendfile`）：

| 路径 | 单流吞吐（8 MiB 段） |
| --- | --- |
| httplib 内容提供者（`pread` + `sink.write()`） | **~1.4 GiB/s** |
| 自持 socket + `sendfile`（极简 HTTP 解析） | **~9.7 GiB/s** |
| ~~差距~~ | ~~**~5–7x**~~ ⚠️ **已作废（见下）** |

> 方法学警告：这两行来自不同探针、不同客户端实现，**不是严格受控对比**。
> 但方向明确且机理清晰（少一次用户态拷贝 + 少一次系统调用）。
> **在 P9 容量门槛中用同一客户端复核**，再据以定稿 ADR-006。
>
> **★ P9 受控复核结果（C9.12，`docs/test-evidence/phase9-adr006.md`）**：
> 上面的 **~5–7x 已作废** —— 它把"sendfile vs pread+write 的 2.05x"与"不同探针的 httplib 数字"
> 拼在一起，**不是受控对比**。用**同一负载生成器 + 独立进程 + 互不重叠绑核**实测：
> httplib 内容提供者 **2387 / 7320 / 6990 MiB/s** vs 裸 socket + `sendfile`
> **5488 / 14785 / 14274 MiB/s**（c1/c4/c16，256 MiB 非稀疏文件，`errs=0`）
> → **2.30x / 2.02x / 2.04x，几何平均 2.12x ≥ 1.5x**。
> 依 C9.12 的规则**采纳 sendfile 方向**（ADR-006 §1），但**实现未交付**，
> 且落地必须与控制面校验**同源**（ADR-006 §4）—— 不采用"独立进程 + 复制一套校验"。

### 1.8 SQLite：小文件写路径的固定成本

每事务 = 写 1 条位置记录 + 1 条元数据记录（模拟 1 个小文件的 DB 成本）：

| 配置 | 吞吐 |
| --- | --- |
| 1 线程 / `synchronous=NORMAL`（WAL） | 21,371 事务/s |
| **8 线程 / `synchronous=NORMAL`** | **25,471 事务/s**（峰值） |
| **8 线程 / `synchronous=FULL`（每事务 fsync）** | **1,219 事务/s** ⚠️ |
| 32 线程 / `synchronous=NORMAL` | 13,475 事务/s（**比 8 线程差**，写争用） |

**三个结论**：

1. `synchronous=FULL` 把上限压到 **~1.2k 小文件/秒**（相比 NORMAL 差 **21 倍**）。
2. WAL + `NORMAL` 下 ~25k 事务/s，**与 §1.5 的 35k req/s 请求率上限同量级** → DB 会成为小文件写路径的瓶颈。
3. **写并发要限流在 ~8**（32 线程反而更差）→ 需要**有界写并发 + 写队列**，而不是让所有请求线程直接抢写锁。

### 1.9 P9 正式容量基线（**产品进程** + 仓库内独立负载生成器）

命令：`scripts/bench_baseline.sh --save`（4 s/点位，全部点位 `errs=0`）。
环境：**WSL2 + 虚拟盘**、loopback、HTTP/1.1 keep-alive、数据面走**真实自签 token 校验**；
服务端 `taskset -c 4-7`、客户端 `taskset -c 8-15`（**不重叠**，铁律 R2）。

每点位重复 **3 次取中位数**（同一次运行内的 3 次散布 <5%）：

| 点位 | 吞吐（中位数） | p50 / p99 | 客户端 CPU |
| --- | --- | --- | --- |
| 控制面读 `GET .../metadata` c1/c4/c16/c64 | 6809 / **13849** / 12636 / 11820 req/s | 105/275 · 212/552 · 938/3646 · 4065/16480 µs | 16% / 50% / 50% / 52% |
| 数据面小对象 GET c1/c16 | 4642 / **16678** req/s | 155/356 · 677/2641 µs | 13% / 89% |
| 数据面 PUT（4 KiB，`per_file`）c1/c16 | 153 / **1355** req/s | 5161/7037 · 9222/12185 µs | 1% / 8% |
| 大文件单流 c1/c4（64 MiB 对象） | **1343** / 3997 MiB/s | 37.5/40.9 · 50.4/59.4 ms | 20% / 203% |
| 上传链 `per_file` c1/c8 | 43.3 / **189.1** files/s | 20.8/24.9 · 34.3/44.6 ms | 1% / 4% |
| 上传链 `per_file`/`batch`/`never` @c4 | **109.9 / 468.6 / 452.0** files/s | 29.0/38.8 · 6.9/11.2 · 7.2/12.4 ms | 2% / 9% / 9% |
| SQLite 写 1/8 线程 | **1446 / 2430** writes/s（1 线程为报告型） | — | — |

**三条读得出来的结论（附适用范围）**

1. **并发：c1→c4 提升明显（6.8k → 13.8k req/s），c4 之后不再提升**（c16/c64 = 12.6k/11.8k），
   而 p99 从 0.28 ms 涨到 3.6 ms / 16.5 ms；客户端 CPU 全程 ≤52%（8 核可用上限）⇒ 瓶颈在服务端侧。
   ⚠️ **"c4 是峰值 / 存在负扩展"在本机无结论**：四次独立运行测到的 c4 分别是
   **14308 / 14140 / 9969 / 13849 req/s**（同一次运行内 3 次重复散布 <5%，**跨会话漂移 ≈40%**，
   本机是共享的 WSL2 主机）。只能保留方向性结论，峰值点位与负扩展需独占硬件复核（C9.14）。
   与 §1.5 的 35k req/s 也不同量级 —— 那是**更简的探针配置**（无鉴权/无 SQLite 读/无审计日志），
   两个数字**不得混用**（旧结论的适用范围已收紧，见 `docs/00-final-design.md` §5）。
2. **fsync 是小文件**写**路径的主成本**：`per_file` 110 files/s → `batch` 469（**4.3×**），
   而 `batch` ≈ `never`（469 vs 452）⇒ 收益来自"摊销 fsync"，不是"放弃耐久性"。
   这是 `storage.posix.durability` 默认 `batch` 的实测依据。
3. **大文件吞吐在本机是内存带宽量级**（1343 MiB/s @c1）：64 MiB 对象全在页缓存里，
   **不能**当磁盘吞吐用；真实存储上的数字见 C9.14（**未验证**）。
4. **单线程 SQLite 写在本机不可复现**（2014~2488 手动复测 vs 359~1503 脚本内）→ 该点位为
   **报告型**（不参与回归判定）；可判定的是 8 线程（2130~2488）。

**这些数字的"能失败"机制**：`scripts/bench_baseline.sh` 内置 p99 阈值表（C9.4）与
"相对基线退化 >20% 即失败"（C9.11）。fsync/磁盘类点位（`data_put_*`/`upload_chain_*`/
`sqlite_write_*`）在 WSL2 上的逐次散布 >20%，因此**只告警不判失败**，
并在脚本与证据里显式标注"该判据需在真实存储上生效"（R4：不把噪声当证据）。

## 2. 原设计的缺陷（逐条对照）

| 原设计内容 | 问题 | 实测依据 |
| --- | --- | --- |
| `server.http.worker_threads: 8` | **8 并发就是天花板**；且注释写的是"线程池"，实际语义是"并发连接数上限" | §1.3 |
| "HTTP 并发：固定大小线程池…阻塞 IO。理由：瓶颈在存储 IO 而非 CPU，代码简单" | 理由前半正确，**结论错误**：线程数直接等于并发上限，配置错误即致命 | §1.3 |
| 未提 `TCP_NODELAY` | **950x** 性能损失 | §1.2 |
| "集中存储模式下服务自身作为数据面" | 正确，但**未意识到每字节占用一个线程 + 无法零拷贝** | §1.4、§1.7 |
| "大文件流式：固定 256 KiB 缓冲，绝不整文件进内存" | 方向正确，但未考虑**并发 × 缓冲**的内存总量，也未指出必须 `pread` 定位读 | §1.6 |
| `gc`/审计/事件在请求路径内同步执行 | 小文件场景下增加固定成本 | §1.8 类比 |
| `fsync_on_write: true` 为全局默认 | 对小文件是**每文件一次 fsync** → 上限 ~1.2k/s | §1.8 |
| `synchronous` 未在配置中体现 | 默认行为不确定（SQLite 默认 FULL） | §1.8 |
| "`fss_http` 负责 Range 归一化" | 过度设计：httplib 已 Range 感知（声明完整大小即可） | §1.6 |
| `idle_timeout_seconds: 60` 对所有端点 | TB 级长传输不能被整体超时打断；需按路由分类 | §1.7 |

## 3. 必须的设计修正

### 3.1 计划新增 ADR-006：大数据面独立进程 + 零拷贝

**决策**：集中存储（POSIX）模式下，**大文件分段读**走一个**独立的数据面监听器**，
不使用 httplib，而是自持 socket + `sendfile`/`splice` + 独立 epoll/线程模型。

理由（全部来自 §1.7 的实测）：
1. httplib 的 `DataSink` 只暴露 `write(data,len)`，**handler 无法获得 socket fd** → 无法零拷贝；
2. 实测 `sendfile` 比 `pread+write` 快 **2.05x**、每 GiB CPU 少 **42%**；
3. 叠加库开销后，自持 socket 的路径比 httplib 内容提供者快 **~5–7x**；
4. 大文件读是**纯带宽**负载，与控制面的 JSON 请求特征完全不同，混在一个线程池里会互相干扰。

**边界（关键：不要把 ADR-002 的教训再犯一次）**：
- **只有** `/api/file/v1/transfer/{token}` 的 `GET`（含 Range）走这条路径；
- 控制面（19 个 OSDU 端点、JSON）**继续用 httplib + `fss_http`**；
- 该数据面的 HTTP 解析必须**极简到只支持所需子集**（`GET`/`HEAD` + `Range` + `Content-Length`），
  并提供与 `fss_http` 相同的硬上限（URI/头长度/超时/并发）；
- 它必须复用**同一套**自签 token 校验与 `IBlobStore` 端口；
- **在 P9 用统一客户端复核 5–7x 差距之后再定稿**；若复核后差距 < 1.5x，则放弃本 ADR，
  统一用 httplib（避免无谓的重复实现）。

### 3.2 并发模型修正

| 项 | 原设计 | 修正 |
| --- | --- | --- |
| 线程池语义 | "worker_threads = 8" | 明确为**并发连接上限**；默认按公式计算，见 §4 |
| 池分离 | 单一池 | **控制面池**（JSON，短任务）+ **数据面池**（字节流，长任务）分离，互不饿死 |
| 准入控制 | 无 | 超过并发上限 → **503 + `Retry-After`**（明确背压），不排队到超时 |
| 连接上限 | 无 | `max_connections` 显式配置；超限拒绝（不 accept 或 503） |
| `TCP_NODELAY` | 未提 | **强制 true**（服务端；客户端同理），并加为阶段 1 门槛断言 |
| 超时策略 | 全局 60s | 按路由分类：JSON 端点 10s；数据面**无整体超时**，只有"空闲无进展"超时（如 60s 无字节流动） |

### 3.3 小文件写路径修正

| 项 | 修正 |
| --- | --- |
| `synchronous` | 默认 **`NORMAL`**（WAL）；配置项 `location.sqlite.synchronous`，并**在启动日志中打印实际值** |
| `fsync_on_write` | 由全局开关改为**分级策略** `fsync_policy: always \| by_size \| never`，配 `fsync_threshold_bytes`（默认如 1 MiB）：小于阈值不 fsync，大于则 fsync |
| 原子写 | 小文件也保留（tmp+rename 是 rename 语义，成本主要在 fsync）；`atomic_write` 保留但 `fsync` 按上一条策略 |
| 写并发 | **有界写并发 = 8**（§1.8 实测峰值），超出排队；禁止所有请求线程直接抢 SQLite 写锁 |
| 批提交 | 位置记录 + 元数据记录可合并为一次事务的地方合并；**文件数据 side 采用 ADR-008 的两阶段批提交**（`durability: batch`，默认批 500） |
| 审计/事件 | 移出请求关键路径 → **异步队列**（有界，满则丢弃并计数；审计可配置 fail-closed） |
| 元数据仓储 | 若目标速率 > 25k 小文件/s，需要**按 partition 分库**或改用嵌入式 KV，列入 P9 评估 |

### 3.4 读路径修正

| 项 | 修正 |
| --- | --- |
| Range 处理 | 声明**完整** `content_length`，由 httplib 计算 `(offset,length)`；`fss_http` 只做越界/416 归一化 |
| 数据读取 | `pread`（定位读，不改变文件偏移，天然线程安全），缓冲从**池**中取（避免每次分配） |
| 零拷贝 | 大文件数据面走 `sendfile`（循环处理 >2 GiB）；文件系统/平台不支持时回退 `pread+write` |
| 页缓存 | 大文件随机读：`posix_fadvise(RANDOM)`；顺序读大段后可 `DONTNEED` 避免污染缓存（可配置） |
| 校验和 | **读路径绝不算校验和**（硬性禁令，见 §1.6） |
| 内存上限 | `buffer_bytes × 并发上限 ≤ transfer_memory_budget`（默认如 256 MiB），启动时校验并在超限时**拒绝启动** |

### 3.5 部署拓扑建议（按负载选模式）

```
场景 A：大量频繁小文件（读写）
  └─ 推荐：对象存储模式（S3/MinIO）
     字节传输走客户端直连预签名 URL → 服务只处理 JSON 元数据
     ⇒ 服务的数据面完全不在路径上，可水平扩展
     ⇒ 若必须用集中存储：小文件写受 §1.8 的 DB 上限（~25k/s NORMAL）约束

场景 B：TB 级大文件分段读（只读）
  └─ 对象存储模式：客户端直接 Range GET，服务零参与（最优）
  └─ 集中存储模式：走 ADR-006 的 sendfile 数据面；单节点带宽约 6–10 GiB/s（本机实测）
     若要更高：数据面可独立水平扩展（无状态，仅需 token 校验 + 存储访问权）
```

## 4. 容量规划公式

```
控制面（JSON 端点）：
  所需线程数 ≈ 峰值并发请求数
  吞吐上限 ≈ min( CPU_核数 / 每请求CPU, 存储/DB 延迟倒数 × 线程数 )
  实测参考：约 200,000 req/s（纯内存 JSON，16 核）；小段读 40,000 req/s

数据面（集中存储）：
  所需线程数 ≈ 峰值并发传输数
  单流吞吐 ≈ 1.4 GiB/s（httplib 内容提供者）或 6–10 GiB/s（sendfile 数据面）
  总吞吐上限 ≈ min( 存储带宽, 网卡带宽, 核数 × 单核吞吐 )
  内存 ≈ 并发传输数 × 缓冲大小（必须 ≤ transfer_memory_budget）

小文件写（每文件固定成本）：
  DB 事务上限 ≈ 25,000/s（WAL+NORMAL，本机）  ← 当前设计的主要小文件瓶颈
  若每文件需要 fsync：上限 ≈ 1,200/s        ← 必须避免逐文件 fsync

大文件分段读：
  单请求开销 ≈ 1.5 ms（1 MiB 段，无读放大）
  请求率上限 ≈ 40,000 req/s（本机，与段大小相关）
```

## 5.5 异步化（协程）决策树

> 完整论证与实测见 **[ADR-007](adr/ADR-007-async-and-coroutines.md)**。探针见
> `docs/appendix/coroutine-probe/`。

```
需要更高并发？
  │
  ├─ 是否已做完这些"免费"的？
  │    □ TCP_NODELAY=true（服务端+客户端）      ← 950x
  │    □ 线程池按"并发连接数"配置（非核数）      ← 线程池=并发硬上限
  │    □ 控制面/数据面线程池分离 + 503 背压
  │    □ SQLite: WAL + synchronous=NORMAL + 有界写并发 8 + 组提交
  │    □ 大文件走 sendfile 数据面（ADR-006）
  │  └─ 否 → 先做完，再重新测量（大概率已够）
  │
  └─ 是 → 检查触发条件（任一满足才考虑协程）
       ├─ T1: 需要维持 > 2,000 个并发连接
       │        （实测：线程模型 2,048 线程时只达 1,273 并发且出错）
       ├─ T2: DB 优化后控制面仍受线程数限制（线程数>512 且 CPU 未饱和）
       └─ T3: 数据面 socket 侧成为瓶颈（存储/网卡未饱和）
            │
            └─ 满足 → 只对【数据面】引入 Asio + 协程，并评估 io_uring
                      异步化 pread/sendfile；**不触碰控制面**
                      （第 3 步：控制面异步化，仅在数据面验证有效后才考虑）
```

**四个必须记住的结论（实测）**：

| # | 结论 | 数字 |
| --- | --- | --- |
| 1 | 协程 + **真异步**：远胜线程模型 | 16 线程 254k req/s vs 2,049 线程 127k req/s（**2x 吞吐 / 128x 线程 / 9x 内存**） |
| 2 | 协程 + **阻塞调用**：**比线程模型更差** | 并发度退化为 io 线程数；实测 763 req/s |
| 3 | 协程 + **offload 到线程池**：等价于线程模型 | 实测 758 req/s；上限 = 池大小，无额外收益 |
| 4 | **协程救不了阻塞的东西** | `pread`/`sendfile`/SQLite/libcurl(easy)/fsync 都是阻塞；除非 **io_uring** 或 offload |

**★ POSIX 集中存储的专项结论**（实测见 [ADR-007](adr/ADR-007-async-and-coroutines.md) §8、
原始输出 `docs/appendix/posix-io-probe/RESULTS.txt`）：

| 单次 I/O | 平均延迟 | 单线程上限 | 该怎么优化 |
| --- | --- | --- | --- |
| 页缓存命中读 4 KiB | **0.7 µs** | 1,534,599 ops/s | **不要异步**（异步是净开销） |
| O_DIRECT 非缓存读 4 KiB | **120.9 µs** | 8,269 ops/s | 线程够用；需 >2,000 并发或想省线程 → **io_uring** |
| **写 4 KiB + fsync** | **1,438.7 µs** | **695 ops/s** | **★ 两阶段批提交（ADR-008），不是异步** |

| 写路径方案 | 文件/秒 |
| --- | --- |
| 1 线程，每文件 fsync | 760 |
| 64 线程，每文件 fsync | 16,104 |
| **io_uring（深度 16，单线程）** | 20,497 |
| **★两阶段批提交（写批 → `syncfs` → 统一 rename → `fsync(dir)`）** | **31,478** ← 比 io_uring 快 1.5x，且**顺序不变量已验证安全**（ADR-008） |
| ~~无数据 fsync + 批末 syncfs~~ | ~~35,389~~ ← ⚠️ **不安全**（违反"数据先落盘再改名"），且只比上面快 11% |

**读路径**：io_uring 用 **1 个线程**达 132,934 IOPS，线程模型用 **128 个线程**才 118,148 IOPS
（设备上限约 136k IOPS / 533 MiB/s，**异步不能突破设备**，只是省线程）。

**三条结论**：① `fsync` 是写入主导成本（1.44 ms），**只有摊销能解决**；
② 缓存命中路径不要异步；③ **io_uring ≠ 协程** —— 实测的 io_uring 收益是用**零协程**的手写
submit/reap 循环拿到的，协程只是让代码好写的语法糖。

**为什么现在不做**：控制面在 pool=512 时已达 **79,970 req/s**，而 SQLite 天花板是 **25,000 tx/s**
（≈5x 差距）→ **瓶颈是 DB 不是线程**；对象存储模式下字节不经过服务 → 协程收益为零。
强行重写 I/O 栈（需放弃 httplib、Boost 头文件 162 MiB、逐个处置阻塞 API）是**负收益的高风险重写**。
